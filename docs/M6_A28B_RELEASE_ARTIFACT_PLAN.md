## Artifact workflow proposed for a later implementation milestone

1. **Freeze source inputs.** Select a reviewed Frontend commit and exact Backend commit. Use the M6-A28D utility to observe clean detached checkouts; its local result still requires separately authorized source identity and review. Record full object IDs, repository identity, submodule state, and source-tree hashes. Confirm the Backend object equals the authorized pin unless a separately reviewed pin change is approved. Keep CI checkout and artifact build inputs identical.
2. **Lock toolchains and dependencies.** Use the Frontend lockfile with a recorded Node/npm version and platform. Add a hash-verified Backend runtime dependency lock/constraints file generated from `pyproject.toml`, including build backend and setuptools; use a fixed Python/pip toolchain. Replace open-ended image/base tags in every release build input with reviewed OCI digests. CI must fail if source metadata and actual checkout disagree.
3. **Build the Frontend candidate once.** Set `AROMAN_RELEASE_SCOPE=public-showcase` and `NEXT_PUBLIC_AROMAN_API_BASE_URL=/api/v1` at build time. Verify metadata and candidate with the existing M6-A25 scripts before containerization. Do not put the private `AROMAN_CATALOG_UPSTREAM_URL`, secret values, or target-specific credentials into the build context or browser bundle. The upstream is runtime-only and must remain `http://catalog-api:8000/api/v1` in the proposed private topology.
4. **Build the restricted Backend image.** Build from the exact clean pinned Backend checkout, using `aroman.exploration_api:app`, not `aroman.main:app`. Install only from the locked dependency set with hashes. Capture build logs and provenance without secrets. Verify the five-route contract against the same pinned source. No locally inferred image hash may be presented as an artifact digest.
5. **Build the database image.** The M6-A27 `Dockerfile.database` adds the reviewed secret-reader group to a PostgreSQL base. Pin the base by digest and record the final built OCI image digest as well as the base identity, PostgreSQL version, Dockerfile/context hash, and build provenance. The Compose variable `AROMAN_POSTGRES_IMAGE` must identify this reviewed final image, not an unpinned tag.
6. **Capture immutable identities.** For every final image, record registry/repository, OCI digest (`sha256:<64 hex>`), platform/architecture, source revision, Dockerfile and context hashes, base-image digests, build tool versions, and SBOM/provenance references. Verify the digest after push and again before promotion/pull. Require signature/attestation verification in the future pipeline; define trusted signer and key custody before accepting it. Never substitute a tag for a digest.
7. **Fingerprint effective Compose.** M6-A28D now renders synthetic default runtime and `controlled-migration` configurations with `docker compose config --format json`, applies `scripts/validate-private-compose.mjs`, normalizes paths, and hashes a deterministic envelope. A future workflow must create separately reviewed release evidence from approved non-secret runtime values, retain any sensitive rendered configuration only in approved restricted storage, re-render at deployment, and compare against a separately approved manifest value. Synthetic M6-A28D fingerprints are not deployment evidence.
8. **Bind build-time and runtime configuration.** Candidate metadata binds public scope and browser API base. The runtime manifest must separately record non-secret runtime settings such as service entrypoint, upstream URL, allowed browser origin, and listening/health behavior. Verify no build-time public variable differs from the approved candidate and that no runtime-only secret/upstream is compiled into `.next`, image layers, logs, or source maps. A config mismatch invalidates the candidate; do not rebuild silently during promotion.
9. **Assemble and review one release manifest.** Extend the existing `docs/private-preproduction-release-record.example.json` mechanism through a separately reviewed schema/script change. Bind source identities, Frontend candidate metadata and artifact digest, all final image digests, Compose digest, dependency lock hashes, migration/schema identity, SBOM/provenance/signature references, backup/restore and rollback references, rights evidence references, builder, deployment operator, and independent reviewer. Use references and hashes, not secret values. Reject placeholders for any mandatory artifact field and do not relax the existing public release gate.
10. **Promote without rebuilding.** Store the signed/approved manifest and artifacts in an owner-selected immutable registry/storage system (provider is undecided). Promotion copies or grants access to the exact digest, never rebuilds or retags as identity. Record prior approved manifest and image digests for rollback. Check forward/backward schema compatibility before migration or rollback; data restore is a separately approved recovery action, not an automatic rollback.
11. **Separate local verification from target acceptance.** CI and isolated local rehearsal may prove source, API contract, artifact metadata, image/config static properties, disposable database privileges, and repeatable smoke tests. They cannot establish Afra capacity, Docker/UFW forwarding, IPv4/IPv6 reachability, Nginx behavior, secret installation, backup recoverability on target, monitoring, or production acceptance. Target evidence requires a separately authorized isolated rehearsal and independent review.

## Proposed manifest identity fields

The existing release-record slots are the starting point, not a new approval path. A future version should schema-validate and bind at least:

| Identity class | Required fields |
| --- | --- |
| Source | Frontend full Git revision and source-tree SHA-256; Backend full Git revision and source-tree SHA-256; Backend pin; clean-checkout attestations. |
| Dependencies/toolchain | Frontend `package-lock.json` SHA-256, Node/npm/platform; Backend lock SHA-256, Python/pip/build backend/platform; relevant build environment identity. |
| Compiled artifact | Frontend scope, browser API base, build metadata version, candidate manifest, compiled artifact SHA-256 and file count. |
| Images | Frontend, restricted catalog API, final PostgreSQL image OCI digests; each platform, Dockerfile/context hash, base digest, SBOM and provenance/signature reference. |
| Runtime config | Canonical effective Compose SHA-256 and source revision; non-secret runtime settings fingerprint; secret names/reference versions only. |
| Database | Alembic head/revision set and schema identity; migrator/runtime identities and independently verified least-privilege grant evidence. |
| Approval/recovery | Builder, operator, independent reviewer, evidence references, previous manifest/digest, approved rollback and backup/restore records, rights review, target evidence package identity. |

No digest, image, signature, manifest identity, target, registry, signer, operator, reviewer or approval is supplied by this planning document.

## Risks, dependencies, and open decisions

- **Backend dependency drift:** `../../Backend/pyproject.toml` declares version ranges (including FastAPI, SQLAlchemy, Alembic, psycopg, and setuptools); no Python lockfile was found in the inspected Backend revision. Container builds can resolve different packages over time. A lock and hash verification require Backend-owner review in a later change; Backend is read-only here.
- **Frontend build reproducibility:** `package-lock.json` and `npm ci` provide locked package resolution, but a stable toolchain, OS/architecture, build environment, and reproducibility comparison still need specification. The candidate source hash includes non-ignored untracked files; a clean controlled checkout must define the source input. The current candidate digest is an integrity identity, not proof two independent builds are byte-identical.
- **OCI artifact provenance:** no images, registry, signer, SBOM policy, signature trust roots, artifact retention policy, or promotion control have been approved or populated.
- **Effective configuration:** Compose validation covers the rendered local input and known policy; any deployment-time override must be rendered, hashed and independently reviewed. Compose rendering does not prove actual daemon networking/firewall behavior.
- **Database state:** Alembic source revisions and isolated grant scripts exist; target schema and actual privileges are unknown. Migration ordering, data compatibility, backup/restore and rollback approvals remain prerequisites.
- **Capacity and protected services:** historical Afra data cannot prove current headroom. Approximately 37 GB root disk/12 GB free is historical; 80 GB expansion is PLANNED ONLY. No automated pruning or unrelated service changes are acceptable.
- **Owner decisions:** D1–D12 remain OPEN; D9 and D12 need eventual public-release disposition. Content rights, target/domain/origin, hosting/network details, spending quote, secret custody, operator/reviewer roles, backup/RPO/RTO, incident response, rollback authority and release GO remain undecided or unverified. Do not turn these recommendations into approvals.
- **Dependency advisory:** GHSA-g3hv-75wg-m249 remains TEMPORARILY ACCEPTED — REMEDIATION OPEN under the role, triggers and closure condition in M6-A28A. Acceptance is not a release waiver.

## Acceptance criteria for a future implementation milestone

1. Proposed schemas and tools reuse the M6-A25 candidate verifier and public-release gate; tests prove incomplete, mismatched, mutable-tag, wrong-pin, unsigned/untrusted and synthetic evidence cannot become production acceptance.
2. Frontend and Backend dependencies/toolchains are deterministically resolved and recorded; Backend changes receive their own authorization and review.
3. One public-showcase Frontend candidate is built and verified once; the correct pinned restricted API image and reviewed custom PostgreSQL image are built from matching inputs.
4. Final OCI digests, signatures/provenance, SBOMs, dependency lock hashes, candidate metadata and canonical effective Compose digest are present and independently verified.
5. Secret content is excluded from source, build args, image layers, browser artifacts, logs and manifests; only approved secret references are recorded.
6. Migration/schema identity, runtime read-only table grants, and separate migration/operator responsibilities have disposable local evidence and approved target evidence where applicable.
7. A non-secret manifest ties all immutable identities to evidence, prior artifact, rollback and recovery references; promotion does not rebuild.
8. Local rehearsal is isolated and reproducible; later separately authorized target rehearsal gathers actual network, capacity, routing, backup/restore, monitoring, secret-delivery and blast-radius evidence.
9. All 13 target controls remain UNVERIFIED until independently reviewed target evidence supports each control. Public release remains NO-GO until existing owner decisions, independent review and explicit owner GO satisfy the unchanged gate.
