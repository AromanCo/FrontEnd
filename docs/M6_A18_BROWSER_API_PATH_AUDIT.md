## Request path as implemented

`src/lib/api/client.ts` defines `browserBase` from `NEXT_PUBLIC_AROMAN_API_BASE_URL`, falling back to `http://localhost:8000/api/v1`. This `NEXT_PUBLIC_` value is substituted into the browser bundle at build time. `AROMAN_API_BASE_URL` is read at server runtime as `serverBase`, but defaults to `browserBase`. `request(path, ..., server)` selects one of those bases based on the call-site boolean. Every fetch sets `credentials: 'include'`, `cache: 'no-store'`, and a 15-second abort timeout. The browser calls therefore go directly from the browser to the configured API origin, with credentialed cross-origin behavior where origins differ. Catalog GETs do not set a custom header; this avoids preflight in the ordinary case, but does not protect the API from non-browser clients.

Server-rendered calls in `src/app/page.tsx`, `src/app/shop/page.tsx`, and `src/app/shop/[id]/page.tsx` pass `server=true` and use `AROMAN_API_BASE_URL`. Client components in `src/components/studio/CreativeStudio.tsx` and `src/components/studio/guided/GuidedStudio.tsx` use the default browser base for families and notes. This splits the live path: server-to-API calls can use a private runtime address, while browser-to-API calls require a browser-reachable API address. The real-stack scripts intentionally build with loopback `NEXT_PUBLIC_AROMAN_API_BASE_URL` and launch a separate loopback API; they do not exercise a deployed gateway or private network.

No Next.js rewrite, API route, middleware proxy, or backend-for-frontend endpoint exists in `next.config.mjs` or `src/app`. `src/proxy.ts` only hides four UI routes when release scope is exploration; it does not proxy API traffic or authenticate users. Its matcher is limited to login, account, cart, and checkout. `AROMAN_RELEASE_SCOPE=exploration` is a server-side UI feature restriction, not an identity or network boundary. M6-A12 explicitly states that hiding controls does not protect Backend endpoints.

The pinned Backend `aroman.exploration_api:app` is the appropriate restricted ASGI target: `aroman/exploration_api.py` exposes exactly five catalog GET route templates, suppresses docs/OpenAPI, validates its route registry and rejects other methods/paths. Its `PublicBoundary` supplies exact-origin credentialed CORS headers for allowed origins. It does not add authentication or network isolation. Full `aroman.main:app` registers auth, user, concepts and health routes, and its separate `CORSMiddleware` is not a substitute for private ingress. Backend configuration requires explicit HTTPS CORS origins in real environments. If the API is kept browser-direct, its CORS origin would need to be the Frontend browser origin; if same-origin proxy is implemented, browser CORS is unnecessary for that path, while the private API still needs appropriate origin policy for any remaining browser paths.

## Feasibility finding

The current application lacks a configured same-origin catalog routing path: `next.config.mjs` has no rewrite and there is no Next.js API route or middleware proxy. This does not establish that a new application handler is required. Because the client concatenates the configured base and path, a relative build-time base such as `/api/v1` is a candidate that may yield same-origin browser requests. An identity gateway or ingress could route `/api/v1` to the private restricted API and other paths to the private Frontend. This routing has not been implemented or tested. The current fallback remains `http://localhost:8000/api/v1`, so a future compiled exploration build must explicitly use a reviewed base and fail its build/release gate if it would fall back to localhost.

Two same-origin implementations remain viable candidates: (A) a narrowly allowlisted Next.js Backend-for-Frontend (BFF) route that forwards to the private API; or (B) gateway/ingress path routing that sends `/api/v1` to the restricted API and other application paths to the Frontend. In either design, identity authorization must run on every catalog API request; a public gateway or same-origin URL does not itself prove that `/api/v1` is protected. The gateway may consume its authentication cookie, but must not forward unnecessary gateway cookies, credentials, authorization tokens or identity assertions to the restricted catalog API. The API must remain private and accept traffic only from the explicitly approved proxy/gateway peer. Evaluate both candidates against the controls below before choosing; neither is selected.

| Control | Next.js BFF candidate | Gateway/ingress path-routing candidate |
| --- | --- | --- |
| Authorization per API request | Gateway authorizes the browser request; BFF endpoint must not be reachable around that gateway. BFF may enforce an additional session check only if its trusted identity mechanism is designed and reviewed; never trust arbitrary identity headers. | Gateway/ingress must apply identity/session authorization to every `/api/v1` request, not just the Frontend document path or initial login. Verify methods and paths are covered by the policy. |
| Exact route/method allowlist | BFF explicitly accepts only five catalog `GET` templates and bounded query values before forwarding; fixed upstream, no generic URL proxy. Backend keeps its own five-route boundary. | Gateway path rule alone is not enough unless it precisely matches the five GET templates, rejects other methods and normalized/encoded variants, and Backend keeps its route boundary. If gateway policy cannot express/verify that rule, this candidate needs an application/API-side enforcement layer. |
| Cookie/session handling | Gateway consumes its browser session. BFF must not forward gateway cookie, Authorization, or identity assertions upstream; its own endpoint remains behind gateway auth on every request. | Gateway consumes its browser session at the edge and forwards only the catalog request. Strip gateway cookies, Authorization and identity assertions before API upstream; ensure API path is not an auth bypass. |
| Forwarding headers | BFF/ingress strips untrusted client forwarding and identity headers; any trusted context is set by the gateway and accepted only from its peer. | Gateway strips client-supplied `Forwarded`, `X-Forwarded-*` and identity headers before setting trusted values; API trusts only the immediate configured peer. |
| Error behavior | Explicitly bound timeout, response size, cache and safe error mapping; fail closed on upstream error without exposing stack/config details. Adds application error-handling code. | Gateway must fail closed on identity/policy/upstream errors, avoid permissive fallback/cache, and return bounded safe errors. Error mapping/config may vary by gateway and must be tested. |
| Route normalization | BFF rejects encoded separators, traversal, duplicate or ambiguous paths and query forms before forwarding; test framework normalization. | Gateway and upstream normalization must agree. Verify raw and normalized path behavior at every hop; reject ambiguity before upstream. This is a key candidate-specific risk. |
| Private-origin isolation and peers | Frontend accepts gateway peer only; API accepts BFF/Frontend service peer only; no alternate origin. API need not accept gateway directly. | Frontend accepts gateway peer only; API accepts gateway/API-routing peer only. Verify gateway-to-API route is private and there is no alternate direct route. |
| Fail-closed | Gateway and BFF deny if identity, policy or upstream is unavailable; no direct API fallback. | Gateway path rule denies if identity service, policy or upstream is unavailable; no path-specific bypass or direct-origin fallback. |
| Operations and maintenance | More app code, deployment/runtime coupling, app-level observability and test surface; route contract can be versioned with Frontend. | Less app code, but more gateway policy/config expertise, path precedence/normalization risk, and possible split ownership between application and edge teams. Gateway behavior changes require regression review. |
| Testability | Unit/integration tests can exercise allowlist, headers and error mapping locally; target tests still needed for gateway session and private peer controls. | Local tests can validate a modeled route table, but actual gateway behavior and identity enforcement require isolated target tests; capture config and probe evidence. |

For either option, SSR calls may continue using the private server-side API base over an explicitly restricted service path. Review host-header/forwarded-header influence and private service discovery. Regardless of routing choice, an exposed gateway edge does not automatically secure the API path: verify that every API request traverses the enforcing identity policy, and independently prove direct API origins unreachable from public and unauthorized peers.

## Existing evidence and limits

Frontend `src/tests/client.test.ts` checks credential inclusion for authenticated operations, error handling and client behavior; it does not establish target credential necessity or a private route. `tests/release-scope.test.ts` and browser journeys cover UI restrictions. `scripts/exploration-real-stack-runner.mjs` starts the restricted ASGI target and compiled Next server on loopback with synthetic/disposable data. Backend `tests/test_exploration_api.py` validates its route boundary; Frontend `tests/integration/test_contract.py` exercises the broader backend contract, not deployed ingress. None of these prove MFA, gateway policy, external reachability, PostgreSQL grants, secret delivery, target TLS, session revocation, backups or incident response.

## Decision

**Current technical gap:** no same-origin catalog routing path is configured, and the client has a localhost fallback. A relative build-time base may support gateway/ingress path routing without new application code, but this has not been implemented or tested. A narrowly allowlisted Next.js BFF remains a viable alternative if selected. In either case, explicitly review the compiled browser base, enforce authorization on every API request, and independently prove API-origin isolation. See [reference architecture](M6_A18_REFERENCE_ARCHITECTURE.md) and [decision brief](M6_A18_IMPLEMENTATION_DECISION_BRIEF.md).
