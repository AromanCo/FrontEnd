### Non-negotiable security boundaries

These requirements carry forward from M6-A15 through M6-A18 and apply to every candidate:

1. Run only the restricted `aroman.exploration_api:app` for this scope. It exposes exactly `GET /api/v1/brands`, `GET /api/v1/products`, `GET /api/v1/products/{product_id}/variants`, `GET /api/v1/fragrance-families`, and `GET /api/v1/fragrance-notes`. Deny other methods, paths, ambiguous or encoded variants, auth/user/concept/OTP, health/docs/OpenAPI, and arbitrary upstreams. The full `aroman.main:app` must not be reachable by testers or public clients.
2. Authorize each catalog API request against the approved person/session and scope. A login page, authenticated Frontend document, same-origin URL, VPN membership, or CORS policy alone does not establish API authorization. Fail closed on identity, policy, gateway, routing, or upstream failure; no unauthenticated fallback or stale permissive authorization.
3. Keep Frontend/API service origins and PostgreSQL private. Deny direct-origin bypass, alternate listeners/previews, management ports, database access, and unrelated peer access. Permit only documented service peers/ports. Public network probes and unauthorized-peer probes must confirm denial. A publicly reachable identity gateway may be evaluated only with per-user MFA, narrow authorization, private origins, per-request enforcement and no bypass; this evaluation is not approval to expose or deploy it.
4. Consume gateway authentication at the enforcement edge. Do not forward gateway cookies, Authorization credentials/tokens, or identity assertions to the catalog API. Strip client-supplied forwarding and identity headers; set trusted values only at the approved proxy and trust only the immediate approved peer. Prove raw/normalized path handling and reject ambiguity.
5. Use HTTPS on approved browser origins, exact-origin CORS where applicable, and no wildcard. CORS is defense in depth, never network isolation. Keep PostgreSQL private and grant the runtime identity only required catalog SELECT access; use a separate, controlled migration identity.
6. Keep credentials out of source, browser bundles, artifacts, logs and evidence. Define secret access, rotation/revocation, audit, backup/recovery, monitoring, incident and release responsibilities before implementation. Retain synthetic data only; any backup exception must be owner-approved and justified under D7.
7. Current Frontend has no configured same-origin catalog route. Browser API base is compiled from `NEXT_PUBLIC_AROMAN_API_BASE_URL`, with fallback `http://localhost:8000/api/v1`. A future exploration build must explicitly set a reviewed browser base and fail build/release if unset, localhost, absolute/unapproved, or otherwise inconsistent with the selected design. SSR private API configuration is a distinct server-side path.

## Access architecture comparison

These are neutral alternatives for the user-to-application access boundary. The hybrid label covers two distinct patterns: split-audience access separates invited testers from operator/admin paths; dual-gated access requires both controls for each scoped user. This distinction follows M6-A17's separation of tester convenience from operator paths and its note that requiring both controls adds setup burden. Neither variant is presumed. All patterns require the service isolation and catalog controls above. Feasibility, identity capabilities, audience fit, operations, privacy, and cost must be evidenced for the eventual candidate; no numeric scores or assumed capabilities are supplied.

| Dimension | Private VPN/network | Identity-protected gateway | Split-audience hybrid | Dual-gated hybrid |
|---|---|---|---|---|
| User path and reachability | Individually enrolled user enters an owner-controlled private network and reaches non-public Frontend ingress. No public application ingress is intended. | User reaches an identity enforcement edge and is authorized for the application; the gateway forwards to private Frontend/API origins. Its endpoint may be publicly reachable. | Invited testers access the exploration app through the identity-protected gateway. Operators and administrators use independently protected private-network paths for their separate duties. | Each individual user must satisfy both private-network and gateway identity controls for the paths in scope. |
| Tester convenience | Client/network onboarding and support are required. | Browser flow may avoid client installation, subject to identity and MFA requirements. | Testers use the gateway browser flow without VPN enrollment; operator/admin convenience is assessed separately. | Testers must enroll/connect to the private network and complete gateway authentication, adding setup, support and access dependencies. |
| Authorization and revocation | Individual identity, MFA, narrow routes, expiry, review, and identity plus network/device revocation; VPN membership alone is not app authorization. | Per-user MFA, narrow application and per-request API authorization, invitation binding, bounded sessions and prompt revocation. | Tester access is individually authorized and revoked at the gateway; operator/admin access is separately authorized and revoked in the private network. Review both rosters and administrative separation; neither audience inherits the other's privileges. | Both controls must authorize the person and relevant path. Revoke identity/session and network/device grants, verify both layers and define the effective revocation target across them. |
| Isolation and security implications | Private origins and narrow routes reduce public app exposure; probe split-tunnel/alternate paths and unauthorized peers. | Public reachability is a material property. Keep origins private and probe direct API/Frontend origins, alternate DNS/IP/ports, previews and unauthorized peers. | Separates tester application access from operator/admin network paths, reducing tester reach to management planes when correctly segmented. The gateway can still be public; prove private origins, role isolation and no bypass. | Independent barriers may contain some single-control failures only if separately enforced and tested. More policy intersections can create misconfiguration, correlated administration or alternate paths; both controls and direct-origin denial require evidence. |
| Privacy and data | Identity/network/device and access logs may be processed; inventory purpose, retention and access. | Gateway/identity may process identifiers, invitations, MFA/recovery metadata, device signals, IPs, auth events and audit/support records. Review processors, locations, retention/deletion and responsibilities. | Gateway identity data for testers plus private-network identity/device/admin records; map each audience's collected data, processors, access and retention. | Combined gateway and network identity/device/session records for each user may increase collection and correlation; minimize, govern and review the combined record set. |
| Operations, failure and support | Enrollment, client/device support, route management, network availability, patching, revocation and incident response. | Gateway policy, identity integration, session lifecycle, public-edge operations, audit export and incident response. | Operate and support the tester gateway and the separate operator/admin private network, with distinct policy owners and incident paths. Outages may affect audiences differently; define each response. | Coordinate gateway and private-network policy, support, outage handling and incident response for every user; either layer's failure may block access, and recovery must not bypass the other. |
| Cost and workload drivers | Access capacity, user/device onboarding, network operations, support, monitoring and operator time. | Gateway/identity capacity, identity lifecycle and support, audit/log retention, privacy review, public-edge operations. | Gateway/identity costs and tester support plus private-network capacity and operator/admin network operations; maintain separation and audit for two audience paths. | Combined access-system costs, onboarding/support for both controls, integration/testing, monitoring, audit and incident coordination; generally greater operational work, subject to candidate evidence. |
| Evidence before owner choice | Named audience feasibility; per-user MFA and route model; peer/port diagram; revocation test; public and unauthorized-peer probes; support/failure plan. | Per-request policy demonstration; MFA/session/revocation and outage tests; privacy/data-flow review; private-origin and bypass probes; policy export and incident plan. | Separate tester and operator/admin role/path maps; gateway tester authorization and revocation; private-path isolation and admin revocation; probes proving no cross-audience or direct-origin access; staffing and cost worksheet. | Demonstrate both factors are required on each scoped user path, test revocation and outages at both layers, probe bypasses, document control independence, usability/support burden, and operational/cost evidence. |

## Same-origin API routing comparison

Routing is an independent decision from the access architecture above. Both candidates remain open. M6-A18 found no configured same-origin catalog route; the current browser base is the compiled `NEXT_PUBLIC_AROMAN_API_BASE_URL` with localhost fallback. A relative `/api/v1` browser base is a candidate only after explicit review and release enforcement. Neither routing candidate is implemented or accepted.

| Control / tradeoff | Narrowly allowlisted Next.js BFF | Identity-protected gateway/ingress path routing |
|---|---|---|
| Request path | Browser calls same-origin Frontend BFF; BFF forwards to fixed private restricted API. Gateway must still guard every request to the BFF. | Browser calls same-origin `/api/v1`; identity gateway/ingress routes allowed API paths to private restricted API and other application paths to Frontend. |
| Per-request authorization | Gateway authorization on every BFF request is mandatory. BFF must not be reachable around the gateway. Any additional BFF identity check needs a separately trusted, reviewed identity mechanism; never trust arbitrary headers. | Gateway/ingress must authorize every API request, including direct same-origin fetches, with current session/role and revocation checks. Protect the API path itself, not only the document/login path. |
| Exact route/method policy | BFF handler enforces only the five exact GET templates, bounded query inputs and fixed upstream; Backend keeps its own boundary. No generic proxy or arbitrary target. | Edge policy must enforce the same five exact GET templates and reject all other methods/paths and normalized/encoded ambiguity; Backend retains its boundary. If edge cannot demonstrate this, the option is not acceptable without separately approved enforcement. |
| Credentials and headers | Edge consumes gateway session. BFF strips cookie, Authorization, tokens/assertions and untrusted forwarding/identity headers; trust only gateway-set context from the immediate peer. | Edge consumes gateway session and strips cookie, Authorization, tokens/assertions and client-supplied forwarding/identity headers before upstream; API trusts only immediate approved ingress peer. |
| Private peers and bypass | Frontend accepts gateway peer; API accepts only BFF/Frontend service peer. Gateway has no direct API route. Probe alternate origins and paths. | Frontend accepts gateway peer; API accepts only approved gateway/API-routing peer. No direct public or unauthorized-peer API route or second bypass. |
| Normalization and failure | Reject traversal, encoded separators, duplicate/ambiguous paths; test framework normalization. Fixed upstream and safe bounded errors/timeouts. Deny on policy, identity or upstream failure; no fallback. | Demonstrate consistent raw and normalized path interpretation across edge and API; reject ambiguity. Prove path policy and upstream failure are closed with no alternate route or permissive cache. |
| Workload and evidence | Adds Frontend code, API contract maintenance and runtime coupling; local allowlist/header/error tests are practical, but gateway and target peer tests remain necessary. | Less Frontend proxy code, more edge-policy ownership and candidate-specific path behavior; modeled tests cannot replace actual gateway, identity and network target tests. |
| Acceptance common to both | Exact five GETs pass and every other method/path is denied before protected handlers; every API request is authorized; private origins and direct-origin bypass denial proven; no secret/credential forwarding; fail closed; M6-A15 target acceptance passed. | Same acceptance criteria. A same-origin URL or successful browser test alone is insufficient. |

## Approval sequence

1. **Documentation review:** owner, architect and relevant security/privacy/operations reviewers review this matrix and linked M6-A15–A18 records; resolve factual corrections and preserve all security requirements.
2. **Architecture decision:** owner records D1–D8 and D10–D11 as applicable, including selected access and routing designs, evidence, scope, limits, accountable roles and date. D9 and D12 remain separate decisions. This step selects a design but does not authorize implementation.
3. **Implementation authorization:** a separate written authorization names permitted work, target boundary, accountable operators, approved spend ceiling and procurement authority, time window, evidence, and stop conditions. No infrastructure, application, DNS, invitations, service exposure or deployment work is authorized before this step.
4. **Technical acceptance:** evaluate the authorized implementation against every applicable M6-A15 gate, including clean-browser synthetic-data scope, five-route allowlist, per-request authorization, network/direct-origin denial, TLS/proxy/CORS, database grants, migration isolation, secrets, backups/recovery, monitoring, rollback and end-to-end browser evidence. Any unexplained failure is no-go.
5. **Private evaluation go/no-go:** accountable owner reviews the complete redacted evidence and signs a separate explicit go/no-go for a bounded private evaluation. Go requires D1/D2 approval and all applicable private-blocking M6-A15 gates passed in the target topology. This is not public launch, real OTP, saved-concept, commerce or broader data approval.

## Stop conditions

Stop and keep the evaluation closed if scope/audience or authority is ambiguous; a D1/D2 boundary is not approved; implementation or spend lacks written authorization; any public or unauthorized path reaches Frontend/API/DB/management/full `aroman.main:app`; per-request identity authorization, exact five-GET allowlist, private origins, credential/header sanitization, direct-origin denial or fail-closed behavior is absent or unproven; unsupported methods/paths or normalization bypass reach a handler; synthetic-data provenance is unclear; a secret or prohibited data appears in client assets/logs/evidence; database runtime grants exceed catalog SELECT; migration/recovery, incident or release ownership is missing; any applicable M6-A15 gate fails or has unexplained results; or observed scope changes to accounts, OTP, persistence, real user data, public exposure or commerce. Revoke access/disable ingress, preserve only approved redacted evidence, notify the designated owner, and require reassessment and explicit authorization before resuming.
