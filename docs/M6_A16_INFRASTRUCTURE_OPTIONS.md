# M6-A16 — Private Infrastructure Options

**Status: comparison for review only. No provider, geography, domain, budget, access method, or architecture is selected or authorized.**

## Decision frame

All options must host the same constrained application boundary: private-access Frontend in exploration mode; catalog requests reach only `aroman.exploration_api:app`; the catalog runtime has SELECT-only access; migrations use a separate identity; and no public route reaches `aroman.main:app`. The data set is synthetic/demo only. These are design requirements from [M6-A14](M6_A14_PRIVATE_EXPLORATION_INTEGRATION.md) and [M6-A15](M6_A15_PREPRODUCTION_READINESS.md), not a deployment topology proven to work.

The agreed planning audience is the project owner, authorized development team members, and individually invited external testers. This is not an approved identity list or technical access decision. The options below are distinct patterns for comparison. Each can still be implemented incorrectly. A private network path and/or identity-based application authorization must be evaluated for browser access, but does not replace service-to-service network isolation, restricted API routing, database grants, or operator access control. CORS is not a security boundary.

## Architecture comparison

| Pattern | Shape and private-access strategies | Security and database placement | Maintenance and reliability | Cost drivers and tradeoffs |
| --- | --- | --- | --- | --- |
| **A. Single isolated host / VM** | One owner-managed host runs reverse proxy, Next.js, restricted FastAPI, and either a local database or a separately attached private database. Reachability could be via owner-managed VPN, a private network, or a separately approved identity-aware access gateway. | Smallest topology, but a single-host compromise or misconfiguration can cross component boundaries. Use host firewalling and process/service identities; keep DB bound to a private interface and enforce separate runtime/migrator roles. A local DB reduces network dependencies but couples backups and failure domains to the host; separate managed DB improves separation at additional operational/cost complexity. | Few components and straightforward deployment, but patching, host hardening, capacity, certificates, backup, monitoring, and recovery are operator responsibilities. Host failure can take down the entire environment. Restoring a host does not automatically prove database consistency. | Compute hours/size, persistent storage, backup storage/egress, VPN or gateway capacity, monitoring, support, and operator time. Lower component count can reduce overhead; concentration increases outage and recovery risk. |
| **B. Private managed application services** | Frontend and restricted API run as separate managed services with private service networking; managed PostgreSQL is reachable only by the API and controlled migration path. Private browser reachability could use a private endpoint plus VPN, or an identity-aware access layer connected to the private service network. | Managed identity/network controls may reduce host administration, but require verification of ingress defaults, service identity, egress, logs, and provider control-plane access. Keep the API service private and ensure the general Backend is not deployed or routed. Place DB on a private managed endpoint; verify role grants, backup controls, encryption/key custody, and restore portability. | Provider handles some host/runtime maintenance and service health, while the team retains application, network, IAM, migration, secret, and incident responsibilities. Reliability depends on service-region design, provider dependencies, quota, and configuration. Managed backups are not accepted until restore evidence exists. | Per-service runtime, DB size/availability tier, private networking/endpoints, identity/access gateway, logs/metrics retention, backups, transfer, support, and minimum monthly allocations. Less host work may trade for more service configuration and provider-specific operational knowledge. |
| **C. Self-managed container cluster or multi-host platform** | Separate web, exploration API, and database workloads across a private cluster or hosts, behind private ingress. Review access via VPN, private client network, or identity-aware gateway. Keep management/control interfaces on a separate restricted path. | Provides stronger workload/network segmentation options if configured and operated correctly. Requires careful cluster policy, secret distribution, node identity, ingress isolation, database network policy, and audit of all paths. DB may run in-cluster or on a separate managed/private DB; in-cluster placement couples operations and may make stateful recovery more demanding. | High operational complexity: platform upgrades, node capacity, certificate and ingress controllers, policy drift, persistent volumes, observability, backup, and incident response. Multiple replicas can improve resilience only when failure domains and stateful dependencies are addressed. | Nodes/control plane, storage, load balancing, private gateway, backup, logs, support, and sustained operator expertise. Can support future scaling/flexibility but may be disproportionate for a small private exploration audience. |
| **D. Private network / owner-operated environment** | Services run on infrastructure already controlled by the organization or its designated hosting partner, with users entering through an existing private WAN/VPN or approved remote-access boundary. Services may use VMs or containers; these are deployment subchoices, not presumed capabilities. | May align with existing identity, network, and data controls. Security depends on inventory, segmentation, patching, remote access, and separation between user, service, DB, and management paths. DB can be a private existing service or a dedicated instance; shared-service tenancy and backup isolation must be explicitly reviewed. | Reuses established operations where they exist, but depends on capacity, change windows, monitoring, recovery practices, and ownership. Reliability and support may be good or weak depending on the current environment; no capability is assumed. | Incremental compute/storage/network, internal labor, licenses/support, backup and monitoring capacity, and any remote-access expansion. Existing sunk costs can reduce incremental spend while limiting flexibility or consuming scarce team capacity. |

The eventual design may combine patterns only after the owner and architect document the resulting data flows, trust boundaries, failure domains, and responsibilities. No pattern is a default or approval.

## Private-access strategies to compare

| Strategy | User path | Benefits | Risks / operating needs |
| --- | --- | --- | --- |
| **Private client network or VPN** | Owner, development members, and individually onboarded testers connect through an owner-controlled private network to non-public Frontend ingress. | Avoids public browser ingress and may align with network controls. Individual identity/device enrollment, MFA support, and group-based routes can be available depending on the chosen service. | Verify whether external testers can be individually enrolled without sharing broad network access; require MFA where supported and approved. Manage invitation/identity verification, expiry, periodic membership review, immediate removal, device/route revocation, access logging, and support. VPN membership must not imply API, DB, deployment, or management access. |
| **Identity-aware application gateway** | Browser authenticates to an application-scoped gateway, which forwards only to the private Frontend; API and database remain on private service paths. | Often supports per-user authorization, MFA policy, individually invited external identities, expiry, access logs, and rapid user revocation. Can separate audience groups at the application boundary. | Verify MFA enforcement and recovery, invitation binding to the intended identity, session duration, fail-closed behavior, upstream header sanitization, audit export/retention, and immediate session/token revocation. Determine whether its public-facing endpoint conflicts with the no-public-deployment requirement; identity protection does not make a publicly routed endpoint non-public. |
| **Existing organization remote-access boundary** | Approved users use an existing managed remote-access system or office network to reach private ingress. | May reuse identity lifecycle, MFA, invitation, support, and incident operations. | Demonstrate that external tester onboarding is supported, individually attributable, time-limited, revocable, and auditable. Verify segmentation prevents tester reachability to infrastructure administration, DB, deployment, and secrets. No such system or capability is assumed to exist. |

### Identity lifecycle and permission separation

Regardless of access mechanism, the selected design must document and test these controls before external testers are admitted:

| Control | Minimum design question / evidence |
| --- | --- |
| Identity and MFA | Is each person individually attributable? Which identities are eligible? Is MFA enforced for owner, team, and external testers, and how are recovery and lost-factor cases handled? Shared accounts are not acceptable for auditable tester access. |
| Invitation and onboarding | Who may invite and approve an external tester? How is the invitation bound to the intended person, accepted once, and prevented from being forwarded or reused? How are identity and scope verified before access is granted? |
| Expiration and review | Does access expire automatically at a recorded date or evaluation-window end? Who reviews active identities and exceptions, and how often? Expiry must not depend only on manual reminders. |
| Immediate revocation | Can the assigned access administrator revoke an identity and active sessions promptly? Evidence should include removal from groups/routes, invalidation of active sessions/tokens where supported, and confirmation that access fails. |
| Permission separation | Define distinct audience, development, release/operator, infrastructure administration, database, and secret-management roles. External testers receive only the exploration audience permission and must have no infrastructure administration, database, deployment, or secret-management privileges. Do not grant these through inherited groups or broad VPN routes. |
| Auditability | Record invitation, approval, grant, authentication/MFA result, role change, expiry, revocation, and administrative actions with person/time/result. Protect audit access, define retention, and test export/alerting. Logs must not capture credentials, tokens, or prohibited personal data. |

These controls describe evaluation requirements, not a selected product or claim that any candidate provides them. D2 remains open for the access mechanism, final authorized identities, reachability, identity rules, and revocation authority.

These approaches can be paired with any architecture row, subject to owner acceptance. The decision must state whether “no public deployment” means no service endpoint on public networks at all, or allows a publicly routed access gateway with strong identity controls; a login-protected public endpoint remains publicly reachable. The owner must explicitly resolve this interpretation. The selected mechanism must also preserve tester/operator separation and support the lifecycle evidence above.

## Cross-option design questions

The selected design must answer these before implementation authorization:

- **Origin, DNS, and TLS:** Who owns any hostname, DNS records, certificate issuance/renewal, and exact browser origins? Can service origins be non-routable outside the approved private path?
- **Ingress and service path:** Which component accepts browser traffic? How is the exact five-route catalog allowlist maintained? How are client-supplied forwarding headers removed, and which immediate peers are trusted? How is bypass to the full app denied?
- **Database:** Is the catalog database ephemeral or retained? Where does it reside relative to API and backup controls? Which specific objects can the runtime read? Who controls migration credentials and recovery?
- **Identity and secrets:** How are owner, development, external tester, operator, service, database, migrator, and secret-manager identities separated and revoked? How are MFA, individual invitations, expiry, immediate revocation, and audit implemented? Where are secrets injected, audited, rotated, and revoked? Are build and browser artifacts checked for secret exposure?
- **Reliability:** What failures are acceptable? What RPO/RTO, maintenance window, restore cadence, capacity, and alert response are approved? Which components are single points of failure?
- **Operations:** Who patches infrastructure and images, reviews deployment artifacts, runs migrations, responds to alerts, handles incidents, and performs rollback? What support is available for the private audience?
- **Cost authority:** What is the approved spend ceiling and who can authorize recurring charges or usage overages? Cost estimates should use the chosen topology, usage assumptions, retention, region, and support level; this document sets no figures.

## Comparison evidence required for a decision

Architect and owner should compare at least two viable patterns against the approved audience and requirements, then record:

1. Component and trust-boundary diagram, peer/port matrix, data-flow and failure-domain notes.
2. Human (owner, development, and external tester), service, database, migrator, and operator access paths, including invitation, MFA, expiry, immediate revocation, least-privilege separation, and audit evidence.
3. Database placement, grant matrix, backup/key custody and isolated restore path.
4. Ingress/TLS/origin design and proof that the full Backend and database have no unauthorized route.
5. Responsibility matrix for patching, secrets, migrations, backups, alerts, incident response, deployment, and rollback.
6. Cost drivers and an owner-approved estimate using explicit assumptions; no budget is implied here.
7. Acceptance test plan mapped to [M6-A15 gates](M6_A15_ACCEPTANCE_GATES.md), including unauthorized network probes and the browser journey.

No row of this comparison constitutes approval or an instruction to provision. The decision record must close D2–D8 and D10–D11 before any implementation phase proceeds; see [scope and approvals](M6_A16_SCOPE_AND_OWNER_APPROVAL.md) and [implementation plan](M6_A16_IMPLEMENTATION_PLAN.md).
