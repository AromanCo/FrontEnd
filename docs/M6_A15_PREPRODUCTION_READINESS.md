## Application boundary and proposed topology

M6-A13's `aroman.exploration_api:app` allows only `GET /api/v1/brands`, `/products`, `/products/{product_id}/variants`, `/fragrance-families`, and `/fragrance-notes`. It has no auth, user, concept, OTP, health, docs, or schema routes and rejects other methods/paths. M6-A14's runner starts that ASGI target, not `aroman.main:app`, uses synthetic seeded catalog data and a disposable SQLite database, and verifies actual browser catalog requests. Frontend `AROMAN_RELEASE_SCOPE=exploration` hides account/login/cart/checkout surfaces and save controls; in-memory Guided-to-Creative transfer is not persistence.

These are application and test boundaries, not a firewall. Backend [M6-A13 boundary](https://github.com/AromanCo/Backend/blob/0be24c4597bd693e70348243c26e550a20a8ad0e/docs/M6_A13_EXPLORATION_API_BOUNDARY.md) explicitly requires a future network design to make the full `aroman.main:app` listener inaccessible from public clients and prevent bypass of the restricted entry point.

Candidate component topology, pending owner/architect decision:

```text
Approved private browser -- HTTPS --> approved ingress --> exploration Frontend
                                                       --> restricted catalog API
                                                           (private service path)
                                                           --> catalog DB (SELECT only)
Operators / controlled release path ----------------------> migration and recovery
```

Do not infer a provider, hostname, region, access product, network ranges, or operator from this diagram. PostgreSQL must be unreachable from browsers and unapproved peers. Ingress must route catalog requests only to the restricted ASGI app; the general Backend app must have no bypass path. An approved secret delivery mechanism, separated migration identity, recoverable database operations, monitoring, incident response, and release/rollback ownership are prerequisites. CORS is not network access control.

## Evidence already available and its limits

Current workflow configures five required jobs; the supplied handoff says all passed at this baseline. `verify` covers typecheck, lint, unit/fixture checks, production build, and Chromium/Firefox/WebKit journeys. `real-stack-browser` and `postgres-real-stack-browser` use local processes/disposable DBs for the full internal app. `exploration-release` exercises compiled exploration UI with fixtures. `exploration-real-stack-browser` uses the restricted API, temporary migrated/seeded SQLite, Next.js, and Chromium. Backend CI additionally configures route, transport, PostgreSQL role-isolation, and backup/restore tests. These establish only tested repository behavior. They do not establish target network rules, TLS, managed PostgreSQL grants, live backup schedule, secret service, monitoring, human response, deployment or rollback.

## No-go conditions

Do not operate even privately while any applicable gate is unknown, missing, or unapproved; D1/D2 scope and access boundary are undecided; the full Backend listener or database is reachable by unauthorized peers; ingress can bypass the restricted API; real user data/auth/OTP is exposed in the exploration scope; runtime credentials are broad/shared or migration credentials are present in the app; HTTPS/origin behavior is unverified; no accountable recovery and incident owners exist; or required restore/rollback tests miss approved objectives. No approval here authorizes provisioning, public exposure, SMS, user accounts, saved concepts, payments, or commerce.

See [owner decision register](M6_A15_OWNER_DECISION_REGISTER.md) and [acceptance gates](M6_A15_ACCEPTANCE_GATES.md). This package waits for architectural and owner review before any later implementation proposal.
